# 关卡系统迭代：完整技术报告

## 零、项目定位

ReverseGen 是为 tile 消除品类游戏设计的牌局生成工具。核心命题：

> 给定地形（牌的空间布局 + 叠压依赖关系），为每张牌赋予花色，使得生成的牌局在**可解性、死亡点位置、决策分支数、难度**等维度上可以被精确、确定性地控制。

旧版 ReverseGen（基于贪心 cost 匹配）无法满足需求——贪心路径 ≠ 真实最优路径。本文档记录从问题发现到新算法设计的完整过程。

---

## 一、游戏规则（精确建模）

### 1.1 核心机制

```
玩家点击单张可点击的 tile → tile 进入手牌区 Dock (上限 7)
  → Dock 中同花色自动检测：有 3 张 → 立即消除（进入 Discard）
  → 消除 3 张 tile 后，被这些 tile 压住的 tile 可能变为可点击
  → 胜利条件：所有 tile 从 Desk + Dock 清空
  → 失败条件：Dock 满 7 张且无任何花色达到 3 张匹配
```

### 1.2 关键约束

- **点击即释放**：tile 被点击进入 Dock 的瞬间，其所压住的 tile 的 RuntimeDependencies 中移除此 tile。释放与消除无关。
- **Dock 满 7 且无匹配 → 死**。第 7 张如果恰好形成匹配则先消后判，不会溢出。
- **只有 RuntimeDependencies 为空的 tile 才是 clickable**。

## 二、项目历程

### 2.1 阶段一：ReverseGen（贪心反向生成）

基于"贪心 = 最优消除路径"的假设，设计了 CostLadder 算法：
- 输入 cost 目标数组，通过贪心选择 + 黑名单封杀 + 池化 + 抢救，使得生成牌局的贪心模拟 cost 链匹配输入
- **成功点**：控制性强，costArray → costLog 匹配率高
- **失败点**：贪心只是牌局全部状态空间的极小一角。DFS 和随机策略能轻松通过贪心无法通过的关卡。贪心域内的控制 ≠ 全域控制。

### 2.2 阶段二：求解器框架移植

将 C# 分析器中的真实游戏引擎移植到 TypeScript：
- `OfflineGame`：使用动态 RuntimeDependencies 的精确游戏模拟
- `DFS 求解器`：状态记忆化 + 死路剪枝，动作排序
- `贪心求解器`：模拟 ReverseGen 假设的策略
- `随机蒙特卡洛`：测量解空间宽度

### 2.3 阶段三：大规模批量分析

分析 2507 个线上牌局：

| 指标 | 值 |
|------|-----|
| DFS 可解 | 97.4% |
| 贪心可解 | 8.4% |
| 贪心失败、DFS 成功 | 89.0% |
| 随机胜率 0% | 99.7% |

**核心发现**：
1. 贪心在 89% 的牌局中失败，ReverseGen 前提不成立
2. 绝大多数线上牌局是极窄的"谜题"——只有极少数的合法消除路径
3. cgEdgeCount（色组依赖 DAG 边数）是最强的区分信号：贪心失败牌局的 cgEdgeCount 平均高 1.81 倍
4. **确定性规则 1**：cgEdgeCount < 30 → 100% 可解（43/43）
5. **确定性规则 2**：colorCount < 8 → 100% 可解（52/52）

### 2.4 阶段四：DAG 分析体系

构建了两级 DAG：

| DAG | 节点 | 边含义 | 用途 |
|-----|------|--------|------|
| 色组 DAG | 花色组 | A → B = A 的部分 tile 阻塞 B 的 tile | 宏观依赖结构 |
| Triple DAG | C(k,3) 个合法 triple | B ≺ A = B.depSet ⊆ A.depSet（偏序） | 消除顺序约束 |

**重要发现**：色组级别的死锁分析（DEADLOCK_CYCLE）假阳性 100%——色组互锁在 tile 级别不一定真正死锁。

### 2.5 阶段五：不可解牌局深度分析

分析 74 个不可解牌局，分类为：

#### Type B：立死型（46/74）
- 开局没有任何花色有 ≥3 张可点击 tile
- 所有可点 tile 分散在多个色——无法凑够任何 triple
- **症状而非病因**

#### Type A：后死型（28/74）
- 至少一色有 ≥3 可点 tile
- 能消除 1~11 步不等
- 死亡发生在链条断裂的那一步

### 2.6 阶段六：死亡链追踪

对所有不可解牌局追踪完整消除链：

```
死亡深度     牌局数
    0         46      ← Type B
    1          8
    2          6
    3          4
    4          2
    5          3
   6-11        5      ← 最深的链
```

**通用死亡模式**：在死亡步，所有剩余色的可点 tile 数均 ≤2。消除最后一个 triple 释放的 tile"散开"到多个色——没有一个色能凑够 3。

### 2.7 阶段七：释放集中度分析

计算每个色的"集中释放"目标：
- "独占阻塞"：颜色 A 是颜色 B 某些 tile 的唯一阻塞者
- 消除 A 的 tile 后，这些独占阻塞的 B-tile 立即变为可点

**死亡步的独占阻塞数**：
```
全 74 个牌局：死亡步的独占阻塞数 avg=0~1, max=2, NEVER ≥3
```

### 2.8 阶段八：确定性死亡条件（100% 验证）

通过一步 lookahead 模拟——消除当前色的 3 张 tile 后，检查是否任意色达到 ≥3 可点：

| 预测方向 | 准确率 |
|---------|--------|
| 延续预测（一步 lookahead 显示有后续） | 72/72 = 100% |
| 死亡预测（一步 lookahead 显示无后续） | 28/28 = 100% |
| **总体** | **100/100 = 100%** |

这一步 lookahead 不需要 DFS——只需检查每个被阻塞 tile 的所有剩余 blocker 是否都在本次消除中。

## 三、核心理论体系

### 3.1 消除链的充要条件

> 链在第 K 步延续 ⟺ 消除第 K 步的 triple 后，至少存在一个色的可点 tile 数 ≥ 3

这等价于：第 K 步消除的 3 张 tile，其作为"唯一剩余 blocker"的 tile 中，至少有一个色获得了 ≥3 张新的可点 tile（包括原有可点 + 新释放）。

### 3.2 死亡位置控制

**死在 step 0**：花色分配使所有色的可点 tile < 3
**死在 step K**：前 K-1 步各解放一个色的 ≥3 可点 tile；第 K 步的 triple 释放后，所有色可点 < 3

### 3.3 自由度 / 解数量

在 step K，若有 N 个色具有 ≥3 可点 tile，则这一步有 N 个可选的分支。
- N = 1：唯一路径（博奕点）
- N > 1：玩家有选择自由
- 全局解空间 = 每步可选分支数的乘积（简化估计）

### 3.4 难度概念

难度 ≠ 权重评分。难度 = 结构性的窄度：
- **低难度**：每步可选分支多，dock 压力低，多条路径通胜利
- **高难度**：每步只有 1~2 个可选分支，dock 压力高，选错即死
- **不可解**：某一步后所有分支都死

## 四、新生成算法 v3

### 4.1 设计原则

- **正向构造**：沿 tile 依赖 DAG 的拓扑顺序，逐步将 clickable tile 分组为 triple
- **每 triple 一个独有色**：简化控制，消除色内多 triple 的复杂度
- **前向正确性**：每一步的选择保证下一步可行——构造即验证，不需回溯
- **死亡 = 停止构造**：在 death step 停止，剩余 tile 分配散色 → 必然无解

### 4.2 输入参数

| 参数 | 类型 | 含义 |
|------|------|------|
| `terrain` | TerrainData | 地形数据 |
| `solvable` | boolean | 牌局是否可解（默认 true） |
| `deathStep` | number | 如果不可解，在哪一步死亡（0 = 立死） |

### 4.3 核心算法

```
1. 构建 Frontier：维护 clickable + onDesk + deps + blocks
2. 正向遍历：
   for step in 0..totalTriples-1:
     if isDeathStep: break  ← 停在死亡步，不再构造
     从 available 中选择 3 个 tile 形成 triple
     分配新独有色
     eliminate：更新 Frontier（释放新 tile）
3. Cleanup：剩余 tile 各自分配独有色 → 无法凑 triple → 必死
```

### 4.4 验证结果（72 牌局 × 12 地形）

| 配置 | 准确率 |
|------|--------|
| SOLVABLE | 12/12 (100%) |
| DEATH-0 | 12/12 (100%) |
| DEATH-1 | 12/12 (100%) |
| DEATH-2 | 12/12 (100%) |
| DEATH 中期 | 12/12 (100%) |
| **全部** | **60/60 (100%)** |

注：死亡步在末尾的配置（DEATH-last）会产生可解板——因为剩余 tile 太少。这是预期行为：剩余 <3 tile 时虽然散色但仍可消完。

### 4.5 自由度与难度

- **自由度**：由 terrain 的依赖层结构决定。每一步 available.size 直接影响可选 branch 数。
  - Branch 数 = floor(available.size / 3)
  - Terrain 的依赖"聚集度"决定了每步释放的 tile 数
  - 当前算法不主动控制自由度——它接受 terrain 的自然结构
  
- **难度** = 窄度 + dock 压力：
  - 低难度：每步 branch 多，DFS 状态数 <100
  - 高难度：每步 branch 少，DFS 穷举需 100K+ 状态
  - 死亡板需要 DFS 穷举所有分支才能判定无解

### 4.6 为什么不需要回溯

- 正向构造保证每一步的 triple 都是合法可点
- 死亡通过"停止构造 + 散色"保证——不需要事后验证
- 可解通过"持续构造直到所有 tile 被分配"保证

## 六、待办路线图

### 6.1 自由度（分支数）控制

**当前状态**：算法接受 terrain 的自然 branch 数（`floor(available.size / 3)`），不主动调节。

**目标**：精确控制每一步有多少个可选的 triple（= 多少个色有 ≥3 clickable tile）。

**实现思路**：
- 控制手段：选择哪些 tile 组合成一个 triple，会影响释放后 available 池的大小和组成
- 想要 branch=1：让释放的 tile 集中在**恰好 1 个未来色**的 3 张 tile 上（独占阻塞恰好 3 张）
- 想要 branch=N：让释放同时覆盖 N 个不同未来色的 tile（每色恰好 3 张）
- 约束：terrain 的依赖结构限制了 tile 的"释放粒度"——一个 triple 消掉后，能释放的 tile 是由地形固定的
- 需要将 tile 到 triple 的分配作为一个约束满足问题：在构造时，根据想要的 branch 数，选择能产生对应释放效果的 tile 分组方式

**验证方式**：生成 branch=[1,2,1,3,...] 的牌局，用 DFS 检查每步的实际可选分支数。

---

### 6.2 共享花色（一色多 triple）

**当前状态**：每个 triple 分配独立色（N/3 种色）。线上牌局通常使用更少的色（每色 6/9/12 张 tile）。

**目标**：支持一个色内有多个 triple，控制色内自由度。

**实现思路**：
- 一个色有 6 张 tile → 色内有 C(6,3) = 20 种 triple 选择 → 增加玩家的色内自由度
- 一个色有 3 张 tile → 色内无自由度，只能消那唯一的 triple
- 构造时需要"合并"多个 triple 到同一色：
  - 同色的多个 triple 必须在 tile 依赖上不会互相死锁
  - 同色的 tile 如果互相阻塞（A 依赖 B），必须先消不依赖别人的那个 triple
- 从独特色开始，生成后合并相邻步骤的色（如果它们的 tile 满足无互锁条件）

**验证方式**：生成的共享色牌局，用 DFS + 色组 DAG 分析自由度分布。

---

### 6.3 Dock 压力控制

**当前状态**：生成时未检查 dock 溢出。DFS 验证时会自然暴露溢出问题。

**目标**：确保生成的牌局在每一步消除过程中 dock 不会溢出（或精确控制溢出位置）。

**实现思路**：
- 在构造的每一步，追踪 dock 状态：
  - 收集 triple 的 3 张 tile 时，每张进 dock
  - 收集过程中释放的 tile（blocked→clickable）不直接进 dock——只有被点击才进
  - 但如果同一色已有 2 张在 dock，第 3 张凑成 triple 自动消除 → dock 减小 3
- 验证：每一步的 `cost`（新释放的 tile 数）≤ `7 - dock.size`
- 如果某步超出，调整 tile 分组以减小该步的释放量
- 也可以设计"必然溢出"的死亡步：控制某步的释放量 > 剩余 dock 容量

**验证方式**：贪心模拟器已输出 costLog + dockLog，可直接检查。

---

### 6.4 解空间分析（解数 / 唯一解）

**当前状态**：未分析生成牌的精确解空间。

**目标**：知道生成的牌局有多少条合法消除路径、是否有唯一解。

**实现思路**：
- 使用 exhaustive DFS（`deep-v3.ts` 中的方法）统计解数
- 唯一解的充分条件：每一步只有 1 个 branch（branch=1 全程）
- 多解的充分条件：存在某步 branch > 1，且不同分支都通向胜利
- 解数上界 = 每步可选 triple 数的乘积（简化估计）
- 精确解数：需要在生成后跑穷举 DFS（已实现，但对宽板会很慢）

**验证方式**：对 branch 可控的板跑穷举 DFS，验证解数与预期一致。

---

### 6.5 博弈点设计

**当前状态**：未实现。

**目标**：在某一步创造"选 A 则死、选 B 则活"的博弈结构。

**实现思路**：
- 在第 K 步，让两个色同时有 ≥3 clickable（branch=2）
- 颜色 A 的 triple 消除后，释放的 tile 能继续链 → 胜利
- 颜色 B 的 triple 消除后，释放的 tile 散开 → 死亡
- 实现：A 的 tile 是最佳释放路径（独占阻塞集中），B 的 tile 是散释放（独占阻塞分散或无）
- 构造时：在目标 step 故意提供 2 个可选色，一个指向胜利，一个指向死亡

**验证方式**：DFS 的 branchStates 记录每一步的分支状态，可直接看出博弈点是否存在。

---

### 6.6 难度曲线

**当前状态**：未实现。

**目标**：控制牌局从简单到困难的过渡曲线。

**实现思路**：
- 难度 = 窄度（branch 少）+ dock 压力（释放量大）+ 容错率（错误分支的后果）
- 简单段：branch 多、dock 压力低、错分支仍可恢复
- 困难段：branch=1、dock 压力高、错分支必死
- 在前几步容易（多 branch），逐渐收窄（减少 branch），最终收束到唯一解或死亡
- 参数化：`difficultyCurve: {step: number, branch: number, pressure: number}[]`

**当前状态**：72 个牌局 × 12 地形。

**目标**：覆盖更多地形、更多参数组合，确保无边界 bug。

**实现思路**：
