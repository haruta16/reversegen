# 关卡系统迭代：完整技术报告

## 零、项目定位

ReverseGen 是为 tile 消除品类游戏设计的牌局生成工具。核心命题：

> 给定地形（牌的空间布局 + 叠压依赖关系），为每张牌赋予花色，使得生成的牌局在**可解性、死亡点位置、决策分支数、难度**等维度上可以被精确、确定性地控制。

旧版 ReverseGen（基于贪心 cost 匹配）无法满足需求——贪心路径 ≠ 真实最优路径。本文档记录从问题发现到新算法设计的完整过程。

---

## 一、游戏规则（精确建模）

### 1.1 核心机制

```
玩家点击单张可点击的 tile → tile 进入手牌区 Dock (上限 7)
  → Dock 中同花色自动检测：有 3 张 → 立即消除（进入 Discard）
  → 消除 3 张 tile 后，被这些 tile 压住的 tile 可能变为可点击
  → 胜利条件：所有 tile 从 Desk + Dock 清空
  → 失败条件：Dock 满 7 张且无任何花色达到 3 张匹配
```

### 1.2 关键约束

- **点击即释放**：tile 被点击进入 Dock 的瞬间，其所压住的 tile 的 RuntimeDependencies 中移除此 tile。释放与消除无关。
- **Dock 满 7 且无匹配 → 死**。第 7 张如果恰好形成匹配则先消后判，不会溢出。
- **只有 RuntimeDependencies 为空的 tile 才是 clickable**。

## 二、项目历程

### 2.1 阶段一：ReverseGen（贪心反向生成）

基于"贪心 = 最优消除路径"的假设，设计了 CostLadder 算法：
- 输入 cost 目标数组，通过贪心选择 + 黑名单封杀 + 池化 + 抢救，使得生成牌局的贪心模拟 cost 链匹配输入
- **成功点**：控制性强，costArray → costLog 匹配率高
- **失败点**：贪心只是牌局全部状态空间的极小一角。DFS 和随机策略能轻松通过贪心无法通过的关卡。贪心域内的控制 ≠ 全域控制。

### 2.2 阶段二：求解器框架移植

将 C# 分析器中的真实游戏引擎移植到 TypeScript：
- `OfflineGame`：使用动态 RuntimeDependencies 的精确游戏模拟
- `DFS 求解器`：状态记忆化 + 死路剪枝，动作排序
- `贪心求解器`：模拟 ReverseGen 假设的策略
- `随机蒙特卡洛`：测量解空间宽度

### 2.3 阶段三：大规模批量分析

分析 2507 个线上牌局：

| 指标 | 值 |
|------|-----|
| DFS 可解 | 97.4% |
| 贪心可解 | 8.4% |
| 贪心失败、DFS 成功 | 89.0% |
| 随机胜率 0% | 99.7% |

**核心发现**：
1. 贪心在 89% 的牌局中失败，ReverseGen 前提不成立
2. 绝大多数线上牌局是极窄的"谜题"——只有极少数的合法消除路径
3. cgEdgeCount（色组依赖 DAG 边数）是最强的区分信号：贪心失败牌局的 cgEdgeCount 平均高 1.81 倍
4. **确定性规则 1**：cgEdgeCount < 30 → 100% 可解（43/43）
5. **确定性规则 2**：colorCount < 8 → 100% 可解（52/52）

### 2.4 阶段四：DAG 分析体系

构建了两级 DAG：

| DAG | 节点 | 边含义 | 用途 |
|-----|------|--------|------|
| 色组 DAG | 花色组 | A → B = A 的部分 tile 阻塞 B 的 tile | 宏观依赖结构 |
| Triple DAG | C(k,3) 个合法 triple | B ≺ A = B.depSet ⊆ A.depSet（偏序） | 消除顺序约束 |

**重要发现**：色组级别的死锁分析（DEADLOCK_CYCLE）假阳性 100%——色组互锁在 tile 级别不一定真正死锁。

### 2.5 阶段五：不可解牌局深度分析

分析 74 个不可解牌局，分类为：

#### Type B：立死型（46/74）
- 开局没有任何花色有 ≥3 张可点击 tile
- 所有可点 tile 分散在多个色——无法凑够任何 triple
- **症状而非病因**

#### Type A：后死型（28/74）
- 至少一色有 ≥3 可点 tile
- 能消除 1~11 步不等
- 死亡发生在链条断裂的那一步

### 2.6 阶段六：死亡链追踪

对所有不可解牌局追踪完整消除链：

```
死亡深度     牌局数
    0         46      ← Type B
    1          8
    2          6
    3          4
    4          2
    5          3
   6-11        5      ← 最深的链
```

**通用死亡模式**：在死亡步，所有剩余色的可点 tile 数均 ≤2。消除最后一个 triple 释放的 tile"散开"到多个色——没有一个色能凑够 3。

### 2.7 阶段七：释放集中度分析

计算每个色的"集中释放"目标：
- "独占阻塞"：颜色 A 是颜色 B 某些 tile 的唯一阻塞者
- 消除 A 的 tile 后，这些独占阻塞的 B-tile 立即变为可点

**死亡步的独占阻塞数**：
```
全 74 个牌局：死亡步的独占阻塞数 avg=0~1, max=2, NEVER ≥3
```

### 2.8 阶段八：确定性死亡条件（100% 验证）

通过一步 lookahead 模拟——消除当前色的 3 张 tile 后，检查是否任意色达到 ≥3 可点：

| 预测方向 | 准确率 |
|---------|--------|
| 延续预测（一步 lookahead 显示有后续） | 72/72 = 100% |
| 死亡预测（一步 lookahead 显示无后续） | 28/28 = 100% |
| **总体** | **100/100 = 100%** |

这一步 lookahead 不需要 DFS——只需检查每个被阻塞 tile 的所有剩余 blocker 是否都在本次消除中。

## 三、核心理论体系

### 3.1 消除链的充要条件

> 链在第 K 步延续 ⟺ 消除第 K 步的 triple 后，至少存在一个色的可点 tile 数 ≥ 3

这等价于：第 K 步消除的 3 张 tile，其作为"唯一剩余 blocker"的 tile 中，至少有一个色获得了 ≥3 张新的可点 tile（包括原有可点 + 新释放）。

### 3.2 死亡位置控制

**死在 step 0**：花色分配使所有色的可点 tile < 3
**死在 step K**：前 K-1 步各解放一个色的 ≥3 可点 tile；第 K 步的 triple 释放后，所有色可点 < 3

### 3.3 自由度 / 解数量

在 step K，若有 N 个色具有 ≥3 可点 tile，则这一步有 N 个可选的分支。
- N = 1：唯一路径（博奕点）
- N > 1：玩家有选择自由
- 全局解空间 = 每步可选分支数的乘积（简化估计）

### 3.4 难度概念

难度 ≠ 权重评分。难度 = 结构性的窄度：
- **低难度**：每步可选分支多，dock 压力低，多条路径通胜利
- **高难度**：每步只有 1~2 个可选分支，dock 压力高，选错即死
- **不可解**：某一步后所有分支都死

## 四、新生成算法设计

### 4.1 输入参数

| 参数 | 含义 | 示例 |
|------|------|------|
| `terrain` | 地形数据 | tile 布局 + 依赖关系 |
| `solvable` | 牌局是否可解 | true / false |
| `deathStep` | 如果不可解，死在第几步（0 = 立死） | 3 |
| `freedomProfile` | 每一步有几个可选色（分支数） | [1, 1, 2, 1, 1] |
| `maxDockPressure` | 最大 dock 压力 | 5 |

### 4.2 核心策略：前向构造 + 一步验证

不是"生成后验证"（backtracking），而是"构造中内建正确性"：

1. 从地形初始化：计算所有 tile 的初始可点状态
2. 逐步构造消除序列：
   a. 根据 `freedomProfile[step]` 确定这一步需要多少个色有 ≥3 可点
   b. 选择一个色作为"正解路径"的下一个 triple
   c. 为这 3 张 tile 分配一个独有色
   d. 一步 lookahead 验证：释放效果符合下一步的 freedomProfile 要求
   e. 更新可点状态
3. 到达终态时，验证所有 tile 已被分配

### 4.3 为什么不需要回溯

- 每一步的可行性由一步 lookahead 实时保证
- 自由度通过控制"有多少色达到 ≥3 可点"实现——在构造时直接选择/避免
- 死亡点通过确保某步释放后所有色 <3 实现
- 每一层约束都在构造时满足，不存在"构造完成后再验证"的需求
