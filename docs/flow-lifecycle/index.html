图1 · 一关的完整生命周期

两个机制来源（地形 tile 摆放 + 外部注入）在 validateMechanicCounts 做一致性校验（tile-count 必须相等，泡泡39 豁免），通过后 formatBoardSpec 组合成 code@31:3,39:2，再进入跑关/求解链路。

图2 · 运行期对象图

以 OfflineGame 为核心：聚合 OfflineTile（内含 TileExtra），持有 MechanicEngine（泡泡状态 + MATCH_BEHAVIORS 策略表）；机制步骤经 STEP_APPLIERS 分发，工具函数与派生随机（extraActionSeed + DotNetRandom）在引擎与步骤侧共用；求解器通过 clone 分支操作对局。

图3 · 单次点击的动作时序

每次点击走完 ①→⑧：收集 → 挂件回调 → 三消判定 → 机制 onMatch → 步骤应用（记入 mechanicLog）→ 状态重算 → 衰减 → 泡泡 tick 至静止。动作与机制步骤统一计数 actionCount，参与派生种子，保证与 Unity 逐位对齐。
